1. 真实问题：一句“修复 Bug”怎样变成可验证的代码更改

用户要求修复 Python average 函数，其中 // 整除会丢失小数。对于 Coding Agent，这不是一次文本生成：Agent 首先需要读取代码和测试，选择命令取得可观察反馈，再决定修改范围、运行测试并提交结果。即使模型准确识别问题，如果容器挂载目录不允许写入，修复仍不能完成。CA-01 的成功轨迹与权限失败轨迹正好展示了这一点。

本研究将“Agent Loop”限定为模型决策与外部工具结果之间的反复交互；不把它等同于智能规划、长期记忆或多 Agent 协作。

3. 源码走读：每一轮的确切调用关系

3.1 run()：初始化、循环与终止

DefaultAgent.run(task) 把任务写进模板变量，清空并初始化 self.messages，追加 system 与 user 消息；随后在 while True 中调用 step()。每一轮在 finally 中执行 save(self.config.output_path)，并在最后一条消息角色为 exit 时跳出。这个结构解释了为什么轨迹既包含连续的模型/环境反馈，也包含终止记录。

run() 分别处理 FormatError、InterruptAgentFlow 和其他异常。格式错误可能进入反复格式失败退出分支；InterruptAgentFlow 把携带的消息追加到记录；未捕获异常被记入轨迹后仍会抛出。并非所有结束都表示修复完成。

3.2 step()/query()：限额和模型决策

上游 step() 的核心只有一行：

pythonreturn self.execute_actions(self.query())

query() 在发起模型调用之前检查 step_limit、cost_limit 和 wall_time_limit_seconds；限额满足退出条件时生成相应的 LimitsExceeded 或 TimeExceeded。通过检查后才增加 n_calls，调用 model.query(self.messages)，累加模型响应上的估算 cost，并把响应加到消息历史。这里的费用检查基于已累计费用，而不是提供商实时强制封顶：最后一次请求可能使累计估算超过阈值，下一轮才停止。

3.3 execute_actions()：消息动作与工具执行

execute_actions(message) 遍历 message.get("extra", {}).get("actions", [])，把每个动作交给 env.execute(action)，随后用 model.format_observation_messages(...) 将执行结果转成模型可读的观察消息并追加到历史。因此一条模型消息不意味着恰好执行一个命令。若执行器抛出 Submitted，控制流被打断，由 run() 的中断分支保存 exit 消息；该提交动作不必产生常规的 observation。

3.4 DockerEnvironment：容器进程与命令执行

DockerEnvironment._start_container() 启动一个保持存活的容器；execute() 用 docker exec -w <cwd> 将模型提出的命令交给容器内解释器执行，捕获合并后的 stdout/stderr、returncode 或执行异常，再调用 _check_finished()。注意默认解释器配置为 ["bash", "-lc"]；实际镜像必须提供可用的 bash，否则需显式调整解释器。上游默认 Docker run_args 包含 --rm，研究脚本覆盖 run_args 时应自行确认资源回收行为与容器清理。

_check_finished() 只有在工具输出第一条有效行等于 COMPLETE_TASK_AND_SUBMIT_FINAL_OUTPUT，且命令返回码为 0 时，才抛出 Submitted 并保存提交内容。这是框架协议上的完成标记，不是外部单测证明。相反，命令非零返回码通常以观察消息形式回送模型，让其有机会下一轮纠正。

3.5 serialize()/save()：证据怎样落盘

serialize() 将 info.model_stats.api_calls、info.model_stats.instance_cost、info.exit_status、messages、trajectory_format、模型与环境信息写入结构化对象；save() 可把 JSON 写到指定路径。数值应读取轨迹而非估算“每轮大约一次工具调用”。输出的路径、模型消息、原始命令可能含敏感信息，分享前需脱敏。

4. 三个真实 Agent 修复任务的可观察轨迹

以下是既有历史实验，不是本次重新执行模型：

| 任务 | 模型调用 | 工具调用 | 宿主独立验收 | 原始证据 |

|---|---:|---:|---|---|

| average 精度 L1 | 7 | 7（第 7 次为提交标记；常规工具反馈 6 条） | 3/3 PASS | Actions 39778338284 ↗ |

| JSON 字段类型 L1 | 6 | 6 | 4/4 PASS | Actions 39780308075 ↗ |

| duration 跨模块 L2 | 7 | 8（第 2 次模型响应有两个动作） | 5/5 PASS | Actions 39782306863 ↗ |

详见 JOB-001F 轨迹对照 ↗，以及 JOB-001C 最早成功/失败对照 ↗。

4.1 L1 average：观察 → 修改 → 验证 → 提交

第一轮列出目录；第二轮读取 calculator.py 与 test_calculator.py，定位 //；第三轮运行测试并复现小数失败；第四轮修改除法；第五、六轮验证并清理临时脚本；第七轮提交。这是 model.query → action → environment output → message history → next query 的直接实例。成功轨迹的结论来自宿主再次执行三个原测试，而不是助手提交宣言。

4.2 L2：跨模块阅读不等于多文件编辑

duration 的真实运行需要跨 config.py → validate.py → duration.py 阅读，测试中 3 项失败、2 项成功；Agent 修正 duration.py 的秒/分钟换算后，独立五项测试通过。这支持“跨模块理解与单文件修改”而不支持“多文件改造已验证”。第二次模型响应含两个工具动作，正好对应 execute_actions() 的多动作执行模型。

4.3 失败对照：错误不一定发生在推理阶段

同一个 average 缺陷的早期失败轨迹 Actions 39777641877 ↗ 显示 Agent 已发现缺陷，但容器进程 UID 0、移除 capabilities，而被挂载的源码目录属于 UID 1001，导致写入权限不足。随后尝试多种修复环境办法仍失败，最后终止于 LimitsExceeded；框架进程退出码也可能为 0，但目标测试依旧 FAIL。后续对齐 UID/GID 1001 并增加容器写入检查，才使成功实验成立。这是执行器条件差异造成的观察性对照，不是“同等条件仅模型随机性造成的失败”。

推荐至少记录 baseline 预期失败、trajectory.info.exit_status、model_stats.api_calls、实际 actions 数、受影响源码文件、git diff、最终独立测试和人为操作。尤其注意 Submitted 代表框架接收到提交协议；它不替代 diff 检查和测试 PASS。模型估算费用不是实际供应商账单。成功个案与失败个案都只有极少样本，不能计算通用 Coding Agent 修复成功率。

7. 技术取舍与边界

最小 Loop 的优点是代码路径短、对模型与工具进行组合较容易、执行轨迹容易审计；边界是命令驱动工具暴露文件系统能力、环境故障可能触发多轮无效动作、单纯预算与步数上限不会自动形成细粒度工具审批、轨迹文件也不等于跨进程 checkpoint 恢复。容器 --network none、--cap-drop ALL、no-new-privileges、非 root、限定挂载等配置减少风险，但不能承诺“绝对安全”；运行受信任镜像，并避免将主机 Docker Socket 或主目录直接挂载给 Agent。

迁移到其他 Coding Agent 时，可以复用“状态/行动/观察/终止/独立验收”分析模型；不宜照搬 mini 的 message["extra"]["actions"] 格式或完成标记协议。对 Aider、OpenHands 需要单独定位其执行状态机、编辑接口与终止条件。
