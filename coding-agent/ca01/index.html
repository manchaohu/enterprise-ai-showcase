CA-01｜Coding Agent 执行循环架构与实现

参考实现：mini-SWE-agent v2.4.6 ｜ 范围：单 Agent、模型决策、Bash 执行、消息反馈、终止与外部验收 ｜ 2026-10-23

系统设计目标：将一项代码修复任务转化为可反复执行、可观察、可约束、可验证的工作循环。模型负责选择下一行动，执行器在隔离工作区运行命令，观察结果回到下一轮模型输入；框架的“任务提交”和外部测试的“修复成功”分别判断。

01｜系统目标与应用场景

典型请求：修复一个计算函数

给定包含 calculator.py 与 test_calculator.py 的 Python 项目，函数 average 使用整数整除 //，导致非整数平均值错误。任务输入为“修复小数精度，保留原测试，运行单元测试后提交”。预期交付是实际源码的最小修改、测试通过结果和可以追溯的 Agent 行动记录。

系统边界内容验收信号
输入任务说明、源代码工作区、模型与工具配置初始测试可复现失败
内部处理模型提出命令 → 容器执行 → 观察反馈 → 下一步每轮状态和反馈可记录
输出源码 diff、轨迹、提交事件、独立测试报告未修改测试；宿主测试 PASS

这里研究的是执行控制的技术机制：它可以处理需要多步探查和修改的任务，但不包含长期任务规划、真正的多 Agent 分工或跨进程检查点恢复。这些能力在本研究中属于其他专题。

02｜总体方案与架构

方案采用五个逻辑模块：任务与策略配置、循环控制器、模型适配器、工具执行环境、独立验收器。前四个形成可反馈的 Agent 内环，独立验收器位于外环；轨迹存储记录两者之间可复核的数据。

逻辑方案图，不代表所有模块都在同一进程：宿主独立验收在 Agent 执行外侧。图中“消息/状态/轨迹”是控制器内部状态和落盘输出，不是单独运行的数据库服务。

模块职责和设计理由

模块职责工程取舍
循环控制器管理消息历史、轮次、时间/费用限制和退出把调度约束从提示词移到程序状态
模型适配器将消息送入 LLM，把响应转换为动作列表对接模型格式，但动作不是实际执行结果
Docker 执行器运行 Bash 命令并返回 stdout/returncode隔离文件写入与命令执行，需预检权限
消息与轨迹把反馈写回下一轮输入并保存 JSON支持诊断，但不等于可恢复 checkpoint
宿主验收在 Agent 外运行原始测试并检查 diff防止只根据“提交成功”错误验收

03｜完整执行时序

以下时序对应已完成的 average 修复案例。一个模型响应可以包含多个命令；时序中的读取、修改与测试是实际任务的动作语义，并非固定的框架工作流。

为解释调用关系而压缩的时序图；完整历史记录有 7 次模型调用，不应把图中的两次示意迭代误当作总次数。

关键反馈闭环：模型只知道历史消息和环境返回的信息。测试失败、权限错误、运行超时都会成为下一轮决策所用的观察结果；如果不把反馈追加到消息历史，下一轮就无法基于刚发生的执行结果调整行动。

04｜状态、接口与终止协议

状态/数据技术含义来源与用途
messagessystem、user、assistant、observation、exit 的有序消息模型每轮依据历史继续决策
n_calls模型请求次数限制步数并统计调用，不是命令数
cost模型返回的估算费用累计预算保护；不等于硬性账单限额
extra.actions本次模型响应中的零个或多个动作动作传递给执行器
output / returncode容器命令执行结果转换为观察消息；非零通常可继续纠错
exit_statusSubmitted、LimitsExceeded 等只表示框架如何结束

执行器识别约定的 COMPLETE_TASK_AND_SUBMIT_FINAL_OUTPUT 首行、且命令退出码为 0 时，触发 Submitted。超出步数/预算等限制则触发 LimitsExceeded。它们表示不同的控制流终点，均不自动证明代码已经修好。

05｜实现位置与关键逻辑

按上述架构定位源码即可理解关键函数之间的关系，而不是孤立记忆函数名。下面的代码是从 v2.4.6 摘取的最小调用骨架，其余状态初始化、格式错误处理和持久化参见原始实现。

# DefaultAgent：循环控制器的核心调用链（节选）
def step(self):
    return self.execute_actions(self.query())

def execute_actions(self, message):
    outputs = [
        self.env.execute(action)
        for action in message.get("extra", {}).get("actions", [])
    ]
    return self.add_messages(
        *self.model.format_observation_messages(
            message, outputs, self.get_template_vars()
        )
    )

整体关系：run() 负责启动与循环；每轮 step() 先通过 query() 请求模型，再通过 execute_actions() 交给执行器；模型适配器将工具反馈组织为下一轮消息。最后由 save() 把状态写为轨迹。这样所有函数都能对应到架构中的一条数据流。

架构位置真实源代码重点阅读
控制器agents/default.py ↗run → step → query / execute_actions → save
执行器environments/docker.py ↗_start_container → execute → _check_finished
模型接口models/ ↗响应解析与 action 格式；不同适配器不同
研究工程agent_run.py ↗准备 fixture、容器配置、CLI、独立测试

最后一行属于私有实验仓库：没有访问权限的读者无法直接打开，公开版以本页说明和上游源码为主。

06｜真实实验及失败分析

案例模型调用实际工具调用独立验收
average 小数精度 L177（含完成标记）3/3 PASS
JSON 字段类型 L1664/4 PASS
duration 跨模块 L2785/5 PASS

这三次使用真实模型的实验分别验证数值修复、严格类型检查与跨模块代码阅读。L2 第二次模型响应包含两个命令，因此 7 次模型 API 调用对应 8 个工具动作。L2 最终只修改 duration.py；跨模块阅读不等于已经验证多文件编辑。

典型失败链：模型定位 // 缺陷 → 尝试修改 → Docker 挂载文件 UID 不匹配 → Permission denied → 多轮环境操作仍无法写入 → 达到步数限制。此例说明执行环境权限是能力的一部分。后来将容器执行用户改为 UID/GID 1001，并进行写入能力预检，才完成成功实验。

原始证据：average 成功运行 ↗、权限失败运行 ↗、L2 运行 ↗。历史 Artifact 可能已过期，现保留结论为已审计的实验记录，不宣称本站重新执行模型。

07｜方案取舍与技术边界

技术选择收益限制
模型决策 + Bash 工具行动空间大，易访问源码与测试命令能力宽，需隔离、最小权限和预算
历史消息反馈简单直观、可解释每轮决策依据上下文随轮数增长，不能替代长期记忆设计
Docker 工作区便于独立运行环境与权限约束UID、镜像、Shell、挂载差异会直接影响成功
外部独立验收结果不依赖 Agent 自称完成只能覆盖现有测试及可定义的质量标准

本方案适合作为单 Agent 代码修复链路、工具执行反馈和技术观测的基础实现。对于人工审批、长任务持久恢复、复杂规划、多 Agent 协作或大型仓库上下文筛选，应再建立相应架构与真实验证，不宜从本案例自动推断已经具备。
