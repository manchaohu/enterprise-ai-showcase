CA-03｜Coding Agent 代码检索与上下文选择

JOB-001S · 2026-10-23 · 参考架构：mini-SWE-agent v2.4.6 / Aider Repository Map

技术目标：当模型接到一个只描述现象、不指出文件位置的缺陷任务时，如何从大量源文件中定位真正负责业务逻辑的实现，选择有限上下文交给模型，并将定位证据与代码变更关联起来。

01｜技术场景与可验收目标

案例：发票金额显示比实际高 100 倍

目标仓库包含 38 个 Python 文件：36 个包模块、入口文件和测试文件。用户只报告“发票总额大 100 倍”，不知道哪一个模块负责金额换算。系统应沿着业务入口 entry.py 追踪到 package_17/processor.py 中的 normalize_invoice_total，确认源数据以 cents 表示却直接作为 dollars 返回。研究任务要求只读定位，不允许修改代码。

可观察的输出应包含：候选文件列表、调用点与定义点、所依据的源码行、打开文件顺序、实际传给模型的上下文大小，以及最终判断是否正确。单纯打印匹配路径，只覆盖其中一个环节。

02｜总体方案架构

工程上可以将代码上下文处理划分为仓库发现、候选生成、关联排序、上下文装配、模型验证五个模块。不同产品会将这些模块合并或采用不同策略；这里是一种可供比较的参考设计，而非声称 mini-SWE-agent 自带全部模块。

关联排序可使用关键词、AST、定义/引用图、路径权重或图排名；对于只使用 Shell 搜索的极简 Agent，并不存在独立的排序服务。

架构模块处理对象质量风险
发现工作区文件、目录、忽略规则漏扫重要代码、读取过量文件
候选函数名、调用点、定义点关键词匹配与实际责任混淆
关联引用边、相关路径、任务提及符号低相关文件占据模型窗口
装配摘要、源码片段、token 上限截断关键实现或边界判断
核验代码位置、测试、轨迹与最终定位推断路径正确却未核实真实调用

03｜两种真实开源实现架构

方案 A：mini-SWE-agent 的命令式仓库探索

mini-SWE-agent v2.4.6 将“需要看什么文件”留给模型，通过 Bash 工具执行 find、grep、sed 等命令，再把结果作为观察消息送回模型。它的核心复用 CA-01 已分析的 DefaultAgent.query → execute_actions → DockerEnvironment.execute 链路。此方案结构简单，检索策略由模型逐步决策；同时，每次 Shell 输出都可能消耗上下文，模型还需要自行追踪候选与调用关系。

方案 B：Aider 的 Repository Map

Aider 在 aider/repomap.py 中提供 RepoMap 机制：提取源文件里的定义与引用标签，在关系图中估计重要文件与符号，按照当前会话文件、提及的标识符和 token 预算生成精简仓库地图。结构化地图并不等于完整源码，它的作用是使模型先获得全局关键符号视图，再针对需要的部分读取完整文件。查看官方说明 ↗。

比较维度mini-SWE-agentAider Repository Map
定位入口模型发出 Shell 搜索命令代码标签、定义/引用关系与仓库地图
上下文构造命令输出作为历史观察消息受 token 预算约束的结构化符号视图
核心控制点工具使用策略、搜索顺序、输出大小解析语言支持、标签质量、图排序、预算
目前本项目证据其他任务有真实文件读取轨迹已有静态源码核查，尚无实际 repo map 输出

证据区分：本章对 Aider 的代码路径和技术机制进行源码级介绍，但没有将 Aider 真实运行或同题比较标记为已完成。本项目 CA-03 的 D2 仍是 OPEN。

04｜数据流、代码位置和关键逻辑

mini 的关键实现：DefaultAgent 从模型接收动作并调用 DockerEnvironment.execute。命令的实际内容由模型决定，框架不预设目标文件；其结果进入消息历史，支持后续读取更精确的源码。

Aider 的关键实现：RepoMap.get_repo_map 是地图生成入口，get_tags 与相关解析代码取得定义/引用标签，排名过程结合引用关系和上下文相关性，最后得到受 token 预算控制的地图文本。这些函数属于同一条“抽取—关系—排序—压缩视图”的链路，不能孤立理解。

06｜技术方案取舍与使用边界

命令式搜索不依赖复杂的代码索引，适合小型仓库、明确错误信息与快速初查；代价是模型自行管理搜索策略，并在每次反馈中消耗 token。结构化 Repository Map 适合存在大量跨文件符号关系、不能把所有源码放进上下文的情形；代价是解析器覆盖范围、标签提取误差、图排序和地图过度压缩都可能影响定位。两者并非只能二选一：工程系统可以先用 Repo Map 建立概览，再用精准文件读取核实代码。

验收时应把“找到符号”“找到真实责任文件”“生成正确修复”划分成不同指标。检索过程的日志应记录读取路径、文件数量、token 数与错误候选；否则即使修复成功，也无法证明究竟是哪一步的检索方法产生效果。

07｜D2 研究缺口与下一实验

  1. 固定本项目 CA-03 生成工作区的 commit、任务描述和只读权限；让 mini-SWE-agent 真实调用模型，只读定位问题，保留脱敏工具轨迹。
  2. 固定 Aider 版本，在同一个工作区生成真实 Repo Map，记录地图内容、大小、符号覆盖及 token 预算，验证是否展示目标函数。
  3. 按相同正确文件标准对照：实际打开文件、无关文件、定位是否准确、成本与上下文大小。不能把机械搜索成功计作 Agent 检索成功。
  4. 满足真实运行、代码路径、轨迹和可复核结果后再审计 D2；本次文档发布不改变 CA-03 当前 D1 评分。
