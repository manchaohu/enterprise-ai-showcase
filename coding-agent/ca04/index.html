CA-04｜Coding Agent 规划与任务分解

专题范围：计划的数据模型、调度算法、执行接口、验收门控和失败重规划。技术机制独立于应用场景展开，实例集中于第 10 节。

01｜设计目标与边界

规划系统将非原子工程需求转成可执行任务图，并对执行顺序、资源、验证及失败恢复提供显式控制。最小闭环是 目标约束 → 计划图 → 就绪调度 → 工具执行 → 证据验收 → 状态更新或重规划。计划不是模型输出的一段文字，而是带版本、状态与验收条件的结构化执行对象。

应区分三层：模型提出候选计划（概率性）；调度器执行依赖约束（确定性）；测试与策略控制是否接受结果（独立验证）。mini-SWE-agent v2.4.6 的默认实现包含模型与工具循环，但不自带本文完整的 DAG 规划系统。下面的系统架构属于可迁移参考设计，不能视作该框架已验证特性。

02｜总体技术架构

规划器与 Agent Loop 不处于同一抽象层：Loop 负责单轮模型决策和环境交互；规划控制面维护跨多轮目标、任务依赖、执行结果与修订版本。执行状态必须独立于聊天文本持久保存，便于验证与恢复。

图中的调度器、计划版本库与重规划器属于参考扩展层；目前已验证的 mini-SWE-agent 内核负责模型查询与命令执行，不可将架构建议记作开源框架原生能力。

03｜任务理解：从需求到可验证约束

职责。从自然语言需求中提取目标状态、范围、禁止行为、验收条件、已知上下文与不确定项。输出的不是任意任务列表，而是可被程序检查的 TaskSpec。如果目标缺少成功条件，后续测试无法判断完成；如果缺少修改范围，Agent 可能把修复测试当作解决问题。

TaskSpec = {
  "goal": "修复既有行为而不修改测试",
  "scope": {"allow": ["src/**"], "deny": ["tests/**"]},
  "acceptance": ["regression_test_pass", "allowed_diff_only"],
  "assumptions": [],
  "unknowns": ["故障根因", "受影响模块"],
  "budget": {"max_steps": 18}
}

算法与验证。模型可提出候选约束，确定性解析器验证字段类型与必填项；系统把验收条件连接到真实测试命令，未知事项保留为待调查任务，不得伪装成已知事实。需求含相互矛盾的指令（例如同时允许和禁止同一路径）应进入冲突裁决，不应直接开始执行。非标准约束必须由系统或人批准，不能让模型自行放宽。

接口。parse_request(request, repo_meta) -> TaskSpec；validate_spec(spec) -> {ok,errors}。记录解析前后的差异，有助于解释计划为什么遗漏步骤。边界：该接口为参考契约，本项目暂无真实 LLM 抽取正确率实验。

04｜计划表示：任务图、版本与状态机

数据结构。节点应包含 id、前置依赖、动作描述、读写资源、预期工件、完成断言和状态。边表达任务先后约束而非简单文本排序。推荐使用 DAG 表达可并行依赖，用状态机表达运行进展。

Plan = {
 "revision": 3,
 "nodes": {
   "inspect": {"deps":[],"status":"done","outputs":["evidence/inspection.json"]},
   "patch": {"deps":["inspect"],"status":"ready","writes":["src/module.py"]},
   "verify": {"deps":["patch"],"status":"blocked","check":"pytest -q"}
 },
 "reason": "发现新增失败测试，重新定位修复范围"
}

状态转移。blocked → ready → running → passed；运行也可进入 failed、needs_review、cancelled。调度器只能根据验收后的状态解锁后继节点，命令退出码 0 不应直接转换为 passed。每次重规划产生新的 revision 和差异，旧执行日志仍保留。

一致性规则。计划节点 ID 稳定、依赖必须存在、无循环引用、完成工件可定位。更新计划时，已经通过的步骤如果依赖或验收规则改变，需要重新标记为待验证，不能盲目继承通过状态。

05｜依赖调度：就绪队列与失败传播

调度策略。对所有未完成节点，只有依赖集合中的节点均 passed 才进入 ready。可以用 Kahn 拓扑排序在 O(V+E) 时间生成合法执行顺序；但多 Agent/并发执行时还必须考虑写资源冲突、配额和执行租约。依赖图是有向约束，而不是任意待办清单。

def ready_tasks(plan):
    passed = {n.id for n in plan.nodes if n.status == "passed"}
    return [n for n in plan.nodes
            if n.status == "blocked"
            and set(n.deps).issubset(passed)
            and not conflicts_with_running_writes(n, plan)]

失败语义。如果 A 失败而 B 依赖 A，B 应保持 blocked；若 A 可重试，重试策略不得自动绕过依赖。无可运行节点时检查是全部完成、循环依赖、缺失前置条件还是执行失败，不应单纯报“没有任务”。

已实现对照。本项目 job001k_planning.py 通过 set 包含判断执行简单拓扑排序，遇到循环/缺失依赖抛错；它没有并发租约、状态机或运行中失败传播。上面 ready_tasks 是参考伪代码，不是仓库已有源码。

06｜工具执行：从计划节点到可观察行动

执行契约。一个节点可以对应多次模型动作，不能假设计划节点等于一次工具调用。执行器须明确工作目录、可写路径、环境变量、timeout、CPU/内存限制和执行主体权限。模型输出应先验证工具 Schema，再进入沙箱。执行后归档命令、退出码、标准输出、文件变化及耗时。

ExecutionRecord = {
 "plan_revision": 3, "task_id": "patch",
 "command": "python -m pytest -q",
 "cwd": "/workspace", "exit_code": 1,
 "stdout_ref": "artifacts/patch-step-3.log",
 "diff_ref": "artifacts/patch-step-3.diff",
 "classification": "test_failure"
}

幂等性与副作用。读取文件可重复执行，写文件、提交 Git、网络操作则可能引入状态变化。应把幂等重试和有副作用的重复执行区分开，必要时使用 checkpoint、工作区快照或 commit SHA 校验。执行中的网络、权限和密钥边界属于工具层的硬性控制。

真实实现。mini-SWE-agent v2.4.6 的 DefaultAgent.execute_actions 将响应中的 actions 交给环境，DockerEnvironment.execute 以 docker exec 运行命令。这证明工具交互存在，但不证明结构化计划节点与工具动作已建立自动关联。

07｜结果验证：局部测试、全局验收与证据

三层验证。①动作级：命令是否运行、文件是否修改；②任务级：该节点的断言、契约和相关测试是否成立；③全局级：原始回归测试、完整差异、边界条件以及禁止修改路径是否满足。动作级 PASS 不得上推为任务级 PASS，Agent 的提交标志也不等于全局验收。

Verdict = {
 "task_id": "verify",
 "command_ok": True,
 "target_tests_pass": True,
 "regression_pass": True,
 "allowed_changes_only": True,
 "artifact_integrity_ok": True,
 "decision": "passed"
}

反馈分类。建议分成工具/权限错误、测试断言失败、依赖或环境缺失、超时/预算触发、目标不明确、结果与证据冲突。不同分类对应不同下一步；例如 Permission denied 应先修执行环境，而不是让模型继续解释业务逻辑。

现有真实证据。CASE-001 的 L1/L2 修复均由宿主独立测试，不仅看模型是否 Submitted。CA-04 自身目前只有确定性三阶段脚本与单元测试，尚无模型自主规划的独立验收。

08｜重规划决策：触发、修订与停止

何时重规划。出现此前未知的依赖、失败分类明确表明当前步骤不可行、工件质量不满足验收或预算不足时，比较继续、重试、改计划与人工接管的成本。重规划必须产生与原计划可比较的增量信息，例如新节点、新依赖、新执行策略或收缩目标，而不是把原命令重复运行。

def decide(feedback, plan, budget):
    if feedback.classification == "permission_denied":
        return "handoff_environment"
    if budget.exhausted:
        return "stop"
    if feedback.adds_new_dependency:
        return "revise_plan"
    if feedback.retryable and feedback.attempts < 2:
        return "retry_with_change"
    return "human_review"

一致性与安全。修订应保留原计划 revision、触发证据、受影响节点和可回退差异，确定哪些已通过任务需要重验。对安全审批、外部副作用和超预算操作不能通过改写计划绕过人工门控。

现阶段边界。这套决策函数是系统设计示例，不是 mini 自带逻辑。JOB-001K 不含真实失败触发的动态计划变更，CA-04 重规划能力仍标记为 OPEN。

09｜模块协同与完整时序

一次完整任务应留下可追溯的链条：request_id → plan_revision → task_id → action_id → observation → verdict → plan_revision'。将每个层次关联，才可解释模型为什么做某事、工具实际做了什么以及是否达到目标。

实现时应给每个执行记录附带计划版本号，防止异步结果写入已废弃计划；恢复后先比对工作区版本、工件 hash 与任务状态，再决定是否重跑。图为参考目标方案，不等于本项目已经实现持久化恢复。

11｜开源实现与后续 D2 实验

源码边界：mini-SWE-agent DefaultAgent 可核查基础 Loop；本项目 job001k_planning.py 的 plan() 是独立的确定性依赖算法；两者尚未接成一个完整的规划控制面。

D2 验证方案：选择具有真实前置依赖的代码修复任务，固定仓库版本及验收测试，让 Agent 提出结构化计划、执行并记录规划与工具轨迹；注入可复现的失败，比较计划 revision 是否变化、受影响的依赖边是否重算及原测试是否通过。同时记录模型调用次数、无效重试次数、工件验证结果与人工干预点。

当前裁决：技术机制文档为 v0.2 待人工审读；工程证据仍是 D1，绝不因为详细架构设计或 HTML 发布而自动提升至 D2。

12｜OpenHands SDK 真实规划实现映射

为补齐本专题的真实开源实现证据，现将 OpenHands SDK 作为实际源码研究对象。已核查两阶段 Planning Agent → Execution Agent、仅可写 PLAN.md 的规划文件工具，以及 TaskAction → TaskExecutor → TaskManager → TaskObservation 子任务链。这些是三项不同技术机制，不能合并表述为已具备自动 DAG 调度器。

上游源码入口：planning preset、restricted plan editor、two-stage example、TaskManager。

已确认的工程细节：规划预设注入五部分 PLAN_STRUCTURE；编辑器经 allowed_edits_files 将写权限限制到计划文件；执行阶段启动新会话并读取计划文件；任务管理器记录 RUNNING、COMPLETED、ERROR 并允许用任务 ID 续接会话。仍缺少：专项真实模型轨迹、自动依赖 DAG、失败触发的真实计划版本变化和独立代码验收。故 CA-04 技术证据仍为 D1，文档真实源码映射进入审读候选。
