CA-04｜Coding Agent 规划与任务分解架构

JOB-001S · 2026-10-23 · 参考实现：mini-SWE-agent 2.4.6 与本项目 JOB-001K 离线实验

核心技术问题：用户提出的工程需求通常不能一步完成。Coding Agent 应识别任务依赖、选择执行顺序、维护各阶段产物，并在失败或新增证据出现时决定重试、修改计划或停止。规划器需要与实际执行器、测试器和状态记录协作，而不是只生成一份待办列表。

01｜系统目标与典型场景

假设用户要求修复一项发票汇总功能：输入的金额以分计价，最终必须以元进行统计。可操作的最小工程链路包含三项具有前置关系的工作：解析原始数据（Parse）→ 金额单位归一化（Normalize）→ 汇总（Aggregate）。如果先汇总再做单位换算，就无法按设计获取正确的标准化数据。

已有 JOB-001K 组件实验输入两笔发票数据（1200、350 cents），期望汇总输出为 {"total":15.5}。这是可以重复执行的离线计算链；真实 Coding Agent 的进一步问题在于：模型是否自己识别出这三个阶段，是否会按测试反馈改变执行安排。

02｜总体方案架构

推荐将多步 Coding Agent 划分为任务理解、计划表示、依赖调度、工具执行、结果验证、重规划决策六个逻辑环节。它们不是 mini-SWE-agent v2.4.6 原生就具有的六个独立服务，而是复杂 Agent 规划系统可采用的技术分层。mini 提供模型与工具交互的基础循环；显式任务 DAG、工件状态和重规划策略必须另外设计或通过支持它们的框架验证。

参考系统方案图。实线表示逻辑信息流；“重规划”是待验证的目标能力，不代表既有 JOB-001K 脚本已经实现自动重规划。

03｜计划数据结构与依赖约束

最小计划可以使用有向无环图（DAG）表示，每个节点至少保留任务 ID、依赖列表与产物。实际多步工程还应记录成功条件、执行状态、失败原因、修改过的文件与预算。不能仅凭自然语言“先 A 后 B”形成可靠可执行计划。

TASKS = {
  "parse":     {"depends_on": [],            "produces": "parsed.json"},
  "normalize": {"depends_on": ["parse"],     "produces": "normalized.json"},
  "aggregate": {"depends_on": ["normalize"], "produces": "result.json"},
}

调度器只有在节点所有依赖完成后才允许执行。当前实验使用 plan(tasks) 对依赖集合进行迭代拓扑排序；若剩余节点没有一个就绪，便拒绝循环依赖或缺失依赖。这里的节点和边均由程序预置，因此只能验证计划依赖机制，不能证明模型能够自行规划。

04｜执行控制、验证和重规划

在真实 Agent 场景下，计划至少要经历“提出方案—执行命令—检查结果—更新任务状态”。下一步应依据可辨识的失败类型决策：例如解析阶段文件格式错误应优先修输入解析，权限不足应检查执行器，业务断言失败应重新定位实现逻辑。任务失败不应直接视为规划错误。

“重规划”应记录触发条件、哪些节点与依赖发生变化、哪些已通过测试必须重验。若只是失败后重新运行同一命令，没有改变计划或获得增量信息，则属于重试，不应统计为成功的重规划。

05｜真实源码和关键实现

研究工程实现：cases/CASE-001-mini-swe-agent/scripts/job001k_planning.py 包含 TASKS、plan、run。最小依赖调度核心如下，执行层再按照顺序读写三个 JSON 文件。关键是 ready 集合由完成依赖决定，而不是程序任意指定排序。

def plan(tasks):
    pending = set(tasks)
    completed = []
    while pending:
        ready = sorted(
            t for t in pending
            if set(tasks[t]["depends_on"]) <= set(completed)
        )
        if not ready:
            raise ValueError("cyclic or missing dependency")
        completed.extend(ready)
        pending.difference_update(ready)
    return completed

开源 Agent 实现边界：mini-SWE-agent DefaultAgent ↗ 的 run → step → query → execute_actions 实现反复决策与工具执行，模型可以在历史消息中自行安排行动，但它没有在该默认循环中内建上述显式 DAG 调度器。将离线 plan() 的能力描述成 mini 自带的功能是不准确的。

真实 L2 轨迹中曾观察到模型读取多个模块、运行测试、修复代码再验证。该轨迹可以说明多步工具行为，却没有证明模型显式生成任务依赖图或在失败时调整计划。

07｜方案取舍与工程边界

方案适用条件限制
隐式规划：模型逐轮选择命令短任务、依赖少、模型能从反馈自然推进难审计计划意图；重试可能无效循环
显式 DAG 计划依赖清晰、步骤多、有确定性工件任务图变化需同步更新，可能过度约束探索
动态重规划 + 验收门控工程任务依赖实际结果变化需要失败归因、状态一致性和重新验收规则

对工程系统，建议把计划视为可修改的执行假设，而不是对模型的绝对承诺。固定的计划适合约束依赖，测试与新证据则决定是否修订计划。复杂需求中还须防止无限规划、任务切分过细和未经授权的文件写入。

08｜从 D1 到 D2 的下一步实验

下一阶段应准备一个固定版本、包含三阶段代码修改和依赖测试的真实任务，提供测试与预算上限；让真实 Agent 自主提出步骤，记录模型输出、执行轨迹和代码更改。随后注入一次明确可复现的中途失败，观察 Agent 是机械重试、使用反馈改动计划，还是明确停止。只有在可以关联“计划—执行—反馈—计划更新—独立验收”的证据链后，才能授予 CA-04 的 D2。
