RAG｜模型检索、证据门控与生成执行

真实 RAG（检索增强生成）实验：解释“先找资料、再给模型、最后核查来源”的工作过程，以及引用为什么不能自动保证正确。

01｜技术需求：按来源资料回答问题

假设一家企业积累了监控文档、工单手册和系统操作说明。员工问：“OpenTelemetry Collector 把追踪数据发往哪里？”如果只是让语言模型凭已有知识回答，模型可能给出通用解释，但无法保证解释对应企业当前实际资料。我们真正想要的是：先从指定的资料库中找出相关内容，再用材料回答，并告诉读者这次用到哪一条证据。

RAG（Retrieval-Augmented Generation）的核心是把检索与生成分成可观察的步骤。 检索负责发现候选材料，生成模型负责把提供的上下文转化为自然语言答案；应用则决定如何连接两者、附加来源以及在证据不足时停止。

02｜技术方案：MiniLM 检索与 FLAN-T5 生成

这次实验不是把四段资料直接贴进提示词，而是使用预训练的 paraphrase-MiniLM-L3-v2 在 CPU 上把问题与文档转成真实的 384 维神经向量。应用通过向量余弦相似度对四份材料排序，保留 Top-3 检索结果，选取排名第一的文档作为生成上下文。

第二个真实模型是 google/flan-t5-small。它读取选中的材料和提问，用预训练权重执行 CPU 生成；程序会把检索到的文档编号附在答案后。编号是应用程序添加的，并非模型自己证明了答案来源。 这是理解工程系统责任边界的关键。

04｜实测结果：生成、拒答与证据绑定

真实运行源码节选，未省略部分请查阅私有仓库：projects/13-real-rag/rag_e2e.py

向量编码与 Top-1 排序

SentenceTransformer 将构造文档和查询编码为归一化向量，矩阵乘法得到余弦相似度，排序同时用文档 ID 消除同分歧义。此工程只有四个构造文档，并未创建向量数据库。

    embedder = SentenceTransformer(EMBED_MODEL, device="cpu")
    doc_vectors = embedder.encode(
        [doc["text"] for doc in DOCS], normalize_embeddings=True,
        convert_to_numpy=True, show_progress_bar=False
    )
    if doc_vectors.shape != (len(DOCS), 384) or not np.isfinite(doc_vectors).all():
        raise RuntimeError("Real embedding dimensions or values invalid")

    tokenizer = AutoTokenizer.from_pretrained(GEN_MODEL)
    generator = AutoModelForSeq2SeqLM.from_pretrained(GEN_MODEL).to("cpu").eval()

    cases = []
    for case in CASES:
        query_vector = embedder.encode(
            [case["question"]], normalize_embeddings=True,
            convert_to_numpy=True, show_progress_bar=False
        )[0]
        scores = doc_vectors @ query_vector
        ranked = sorted(
            zip(DOCS, scores), key=lambda item: (-float(item[1]), item[0]["id"])
        )
        best = ranked[0][0]
        allowed, overlap = evidence_gate(case["question"], best)

应用层拒答门控与生成

证据门控只检查问题与 Top-1 文档共享的非停用词数量，未达门槛由应用直接返回拒答，不调用生成模型；达门槛才将文档和问题装配为 Prompt，经 FLAN-T5 生成。来源 ID 在应用层附加，并非模型自己验证引用。

        if not allowed:
            # This refusal is an APPLICATION guard, not an LLM-generated answer.
            entry["answer"] = "Insufficient evidence in the local knowledge base."
            entry["checks"] = {"unsupported_refused": case["expected_doc"] is None}
        else:
            prompt = (
                "Answer the question using ONLY the context. Give the shortest exact "
                "factual answer. If context does not answer, say unknown.\n"
                "Context: " + best["text"] + "\n"
                "Question: " + case["question"] + "\nAnswer:"
            )
            tokenized = tokenizer(prompt, return_tensors="pt", truncation=True, max_length=384)
            with torch.inference_mode():
                output_ids = generator.generate(
                    **tokenized, max_new_tokens=36, do_sample=False, num_beams=2
                )
            output = tokenizer.decode(output_ids[0], skip_special_tokens=True).strip()
            entry["prompt"] = prompt

工程集成边界

生产集成需补文档权限过滤、检索阈值评估、跨文档召回、引用忠实度检查。词重合不等于语义证据。

Tesseract

关于扫描件 OCR 的提问

问题：Which named OCR engine extracts text from scanned images?

真实生成的关键答案词：Tesseract。应用附加 DOC-OCR。

第三个问题是“Who won the 2030 World Cup?”。因为最相关文档与问题缺少足够的非停用词重叠，应用层证据门控拒绝了这次请求，记录 generation_executed=false；模型甚至没有运行生成步骤。不能把它说成“语言模型自己判断出了未知事实”。

真实工程证据：GitHub Actions #39353359968 完成真实神经检索、真实 FLAN-T5 生成、JSON 证据保存与独立校验。三个测试问题中，两次生成、一次应用拒答。

06｜复现步骤及证据来源

这个实验足以证明一条最小 RAG 链路确实运行：真实文本嵌入、检索排序、证据选取、条件生成以及答案来源关联。但它没有完成大量复杂问题的准确性基准，也没有建立跨段落推理、中文专业知识问答、检索召回率或来源真实性评估。词面重合规则很容易在同义表达或迷惑性问题中误判。

尤其要注意：应用加在答案末尾的 [DOC-OTEL] 只能表明系统选中了这份资料，不能保证答案中的每一句话都由该材料支持。两种模型下载时仍使用动态 main 修订，版本完全不可变的重现条件尚未建立。这是一个清晰但受限的机制演示，不是已达生产质量的企业知识助手。

06｜自己核验：把提问、检索、生成拆开看

工程程序会记录原问题、Top-3 文档 ID 与余弦得分、通过或拒绝证据门控的理由、提供给生成模型的真实提示词、生成原始文本及应用附加来源 ID。读者可以查看这条证据链，逐步分辨“模型执行了什么”与“应用程序做了什么”。
