Demo 08｜推理接口的并发、超时与降级：HTTP 实测

公开在线审读候选（仍待该篇人工内容验收） · 源代码位于私有工程仓库 · 实验结论只适用于声明的验证范围

原始源码（需访问权限）：08-inference-latency　 Actions Run：39224324475

1. 技术需求与验收

在可控制延迟的 HTTP 服务上测量并发响应、请求超时与客户端降级。客户端提交 12 次请求，使用 4 个工作线程；成功路径模拟 25ms 处理延迟，另一次请求故意延迟 400ms，客户端超时设为 80ms，应返回 queued-for-later。这里使用真实 HTTP 和真实耗时测量，但“模型输出”是确定性模拟，不是 LLM 推理性能。

2. 技术方案和数据链路

服务端 ThreadingHTTPServer 监听临时本地端口，处理 /infer POST、检查输入大小和 delay_ms，再构造 classified: 响应。客户端 urlopen 测量耗时，捕获 TimeoutError/URLError 形成降级结果。测试中的 p50/p95 使用简单排序选位函数，不是带统计置信区间的性能压测。

3. 核心实现及关键代码

3.1 服务端延迟与输入限制

对应源码：service.py — 关键代码节选（省略上下文，不可直接独立执行）

size = int(self.headers.get("Content-Length","0"))
if not 0 < size <= 4096: raise ValueError("content length")
delay = float(d.get("delay_ms",0))
if not 0 <= delay <= 1000: raise ValueError("delay range")
time.sleep(delay/1000)
body = json.dumps({"output":"classified:"+str(d["text"])[:40],
                   "engine":"deterministic-mock"}).encode()

以 delay_ms 注入可重复的阻塞时间，方便区分正常和超时路径。Content-Length 上限降低测试接口接收超大请求的风险；模型响应中的 deterministic-mock 是明确证据，绝不能写作真实模型推理。线程化服务与真实 HTTP 能验证客户端的故障处理边界。

3.2 客户端超时和百分位数

对应源码：verify_latency.py — 关键代码节选（省略上下文，不可直接独立执行）

with urllib.request.urlopen(req, timeout=timeout) as resp:
    payload = json.loads(resp.read())
except (TimeoutError, URLError):
    return {"kind":"fallback", "output":"queued-for-later", ...}
# percentile(): ordered[min(n-1,max(0,int((n-1)*p)))]

客户端超时只意味着该请求端不再等待，不保证服务端任务已取消；业务操作存在重复风险时应加幂等 key。该分位数函数采用零起点下标和截断；少量样本的 p95 很容易接近尾部某个点，因此只用于演示检查，不作性能 SLO 承诺。

4. 实验结果与证据

归档 HTTP_LATENCY_FALLBACK_E2E_PASS：12 次成功请求、并发数 4、p50 26.25ms、p95 27.14ms；超时回退 queued-for-later，返回耗时 80.47ms。结果只对应 CI 上的小型本地模拟服务和当前一次测量。

5. 工程使用与集成

接入真正模型推理服务时，应把服务端 sleep 替换为推理调用，把超时层放在 API 客户端并制定取消/降级策略，记录请求 ID、模型版本和错误类型。缓存、排队、并发限流和异步结果查询可以作为后续模块。负载测试需增加分布、持续时间、并发阶梯和超时阈值。
