Demo 06｜Agent 工单审批：请求、批准、一次性消费与审计

公开在线审读候选（仍待该篇人工内容验收） · 源代码位于私有工程仓库 · 实验结论只适用于声明的验证范围

原始源码（需访问权限）：06-agent-approval　 Actions Run：39214083969

1. 技术需求与验收

为关闭工单这类有业务副作用的工具建立审批闸门。Agent 可以申请关闭指定工单，只有 reviewer 身份在程序层批准后，Agent 才可用同一个审批 ID 和原始参数执行一次操作。实验还测试工具白名单、参数绑定、重复消费、未经审批和错误调用身份被拒绝。

2. 技术方案和数据链路

ApprovalGate 使用自己的 SQLite approvals 与 audit 表，同时调用 Demo 01 的 TicketStore 更新工单。审批记录包含 requester、tool、序列化的 args_json 和 state；执行时使用单条条件 UPDATE 从 approved 变为 consumed，同时绑定审批 ID、工具名和参数，从而防止审批被转用于其他工单。身份只是测试中传入的字符串，不是受信任登录体系。

3. 核心实现及关键代码

3.1 申请时限制工具和参数

对应源码：approval_gate.py — 关键代码节选（省略上下文，不可直接独立执行）

if actor != "agent" or tool != "close_ticket" or set(args)!={"ticket_id"}:
    self.record(actor,"DENIED",None,"not permitted for approval")
    raise PermissionError("not permitted")
arguments = json.dumps(args, sort_keys=True)

申请只允许 close_ticket(ticket_id)，其余工具立即拒绝，审计记录事件。sort_keys=True 保证同样 JSON 参数使用稳定序列化，便于后续字节串匹配；真正企业系统还需要类型校验和身份来源可信性。

3.2 一次性消费与审计边界

对应源码：approval_gate.py — 关键代码节选（省略上下文，不可直接独立执行）

db.execute("BEGIN IMMEDIATE")
cursor = db.execute("""UPDATE approvals SET state='consumed'
 WHERE id=? AND requester=? AND tool=? AND args_json=? AND state='approved'""",
 (approval_id,actor,tool,arguments))
if cursor.rowcount!=1:
    db.rollback()
    raise PermissionError("no matching active approval")

条件更新与事务绑定，能防止同一审批在已消费后第二次通过。此 Demo 先在审批库提交 consumed，随后才调用另一份 SQLite 中的工单关闭操作；跨两个数据库不是一个原子事务。若关闭执行失败，审批可能已经消费，业务需要补偿机制或统一事务/Outbox 设计。

4. 实验结果与证据

原始证据 AGENT_APPROVAL_SQLITE_E2E_PASS：单一工单在批准后关闭，记录 APPROVED 与 EXECUTED 各一次，并出现多项 DENIED；同一审批 ID 无法重复使用，参数改为其他 ticket_id 会被拒绝。该 Demo 不涉及真实 LLM 决策或浏览器中的真实人工审批。
