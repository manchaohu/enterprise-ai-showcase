一个问题需要跨越三层关系，系统怎样找到证据？

真实 SQLite 关系图与多跳查询实验：从“找一篇文档”进入“沿着多条事实关系查找路径”，理解图检索的价值与局限。

01｜现实问题：一个答案藏在多份材料中

想象企业排查某个核心服务的故障。运维人员的问题是：“维护这个服务所使用数据库的是哪个团队？”此时，第一份文档可能只写了服务依赖哪个索引组件，第二份写了该组件使用哪个数据库，第三份才写数据库由哪个团队维护。单独阅读任何一份资料，可能都无法直接回答。

图关系查询把问题从“寻找相似文本”扩展为“沿着实体关系寻找证据路径”。 我们可以把服务、索引组件、数据库和团队当作节点；“依赖”“运行在”“负责维护”成为有方向的边。沿着这些边连接，系统就能够回答跨多篇材料的问题。

02｜技术原理：节点、带方向的关系边与原文证据

Demo 27 使用 Python 标准库的 SQLite 保存结构化关系，一条记录包含起点、关系类型、终点、来源文档编号和原文引句。这里没有神经向量，也没有大模型。关系是预先明确整理好的数据，查询时通过广度优先搜索（BFS）寻找有向最短路径。

图中的 Atlas、Beta、Gamma、Echo、Delta 和 Foxtrot 是构造案例中的实体名称，每条连线都对应实验输入中的一条显式关系及来源编号。它们不是从企业文档现场抽取的真实生产拓扑。图形本身是根据 data/evidence.json 中的五条边绘制的真实输入关系图，而不是假想的概念结构。

03｜工程流程：先建立可信关系，再执行有向遍历

① 读取资料
5 篇构造短文
② 校验关系
5 条边与原文匹配
③ SQLite 查询
BFS 找最短有向路径
④ 独立验算
穷举全部候选路径

初始化时，程序要求每条关系引用的文档真实存在，并且附带的引句确实出现在这篇原文中。随后把边加载进 SQLite 内存库，以起点为条件查找下一跳，并在搜索时记录已走过的节点，防止重复访问。达到用户指定的最大跳数，就停止进一步扩展。

这种方法揭示了图查询与文本检索的重要区别：即使两个实体之间没有直接的文本相似性，只要存在受支持的有向关系路径，就可以通过一跳接一跳找到联系。 路径是否合理仍然取决于前期建图是否正确、关系含义是否可信。

实验实测了 4 个查询，包括两个两跳结果、一个三跳结果和一个反向不可达结果。独立验证器并不调用 BFS 的搜索结果来代替验证，而是穷举全部允许长度内的边序列，重新检查最短跳数、关系完整性、引句与原文的对应情况。

真实验收证据：GitHub Actions #39519975527。该运行支持此数据规模下的 SQLite 查询与独立穷举验证，不属于大规模知识图谱性能测试。

05｜能力边界：会走路径，不等于能自动读懂企业资料

这一实验最容易被误读的地方是“图关系”三个字。系统确实执行了真实的关系存储、搜索和引用核验，但它没有执行自动实体识别、自动关系抽取或语言模型生成图结构。五条边都是输入文件里手工明确写出的。当前也不包含自然语言自动转图查询、模糊实体消歧、权限过滤、多用户协同或生产规模评测。

与 GraphRAG 的区别：GraphRAG 类方案通常还需要从大量非结构化材料中构建和维护关系图，并可能将图检索与生成模型结合。Demo 27 只检验其中“带证据的关系遍历”这一明确机制。关系图可能存在错误或过期，这些问题不会因为 BFS 正确执行而自动消失。

06｜想自己检查路径？可以逐条追到原文

打开源码中的 data/evidence.json 可以看到全部五条关系及五份构造原文。运行 graph_e2e.py 将生成查询结果 JSON；再运行 verify_evidence.py，便能观察独立穷举程序如何验证每条路径。整个复现过程只用 Python、SQLite 和标准库，理论上无需 GPU、模型下载、Docker 或收费 API。
