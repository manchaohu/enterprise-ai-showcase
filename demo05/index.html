Demo 05｜SQLite 异步队列：租约、延时重试与死信状态

公开在线审读候选（仍待该篇人工内容验收） · 源代码位于私有工程仓库 · 实验结论只适用于声明的验证范围

原始源码（需访问权限）：05-async-queue　 Actions Run：39211107072

1. 技术需求与验收

将重复业务任务安全地保存到队列，Worker 取任务后可以成功完成、失败延时重试，进程异常时可回收过期租约；达到重试上限后进入 dead。本实验采用 SQLite 数据表模拟一个小规模可持续队列，时间由测试传入逻辑秒数，因此演示的是状态与事务语义，不是生产消息中间件的吞吐能力。

2. 技术方案和数据链路

表 jobs 保留 queued/running/done/dead 状态、attempts、ready_at、lease_until、request_key。提交与领取均执行 BEGIN IMMEDIATE，在 SQLite 写锁内完成选择和更新，以减少两个 Worker 对同一任务的竞争。失败将 attempts 按指数退避映射到下一次可领取时间；租约过期的 running 任务可再次领取。

3. 核心实现及关键代码

3.1 幂等提交与冲突检查

对应源码：queue_store.py — 关键代码节选（省略上下文，不可直接独立执行）

db.execute("BEGIN IMMEDIATE")
db.execute("INSERT OR IGNORE INTO jobs(request_key,payload) VALUES (?,?)",(key,payload))
job = db.execute("SELECT * FROM jobs WHERE request_key=?", (key,)).fetchone()
if job["payload"] != payload:
    db.rollback()
    raise ValueError("idempotency key conflict")

request_key 为 UNIQUE，重复提交相同 payload 返回原记录，重用相同 key 执行不同命令则拒绝。将同一业务操作的重试限制在相同 key 上，能减少重复执行。注意这仅能约束提交，不自动保证对外部系统的副作用 exactly-once。

3.2 租约领取和失败退避

对应源码：queue_store.py — 关键代码节选（省略上下文，不可直接独立执行）

row = db.execute("""SELECT * FROM jobs WHERE
 (state='queued' AND ready_at<=?) OR
 (state='running' AND lease_until<=?)
 ORDER BY id LIMIT 1""", (now,now)).fetchone()
# claim updates attempts and lease_until in the same write transaction
ready = now + (2 ** row["attempts"]) if not dead else now

领取逻辑既覆盖已到期 queued，也覆盖租约已过期的 running。每次 claim 增加 attempts。第一次失败后以 2**1=2 个逻辑秒延时，再次失败同理递增；到达最大次数会进入 dead。生产环境需要明确租约续期、并发 Worker 争用和时钟一致性策略。

4. 实验结果与证据

证据 ASYNC_SQLITE_QUEUE_E2E_PASS：重复提交保持同一 job，冲突 key 被拒绝；延时重试和过期租约重新领取通过；失败任务第三次尝试进入 dead，另一任务成功到达 done。本次没有实测多节点并发、高吞吐或崩溃恢复持久化服务部署。

5. 工程使用与集成

可用于少量异步文件处理、通知或同步作业的状态机原型。接入 HTTP 服务时提交后立即返回 job ID，Worker 定时 claim，前端轮询状态。对重要任务需要去重范围、最大重试策略、死信排障入口、外部幂等令牌与告警；规模化可替换为成熟队列系统。
