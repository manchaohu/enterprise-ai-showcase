1. 技术需求与验收条件

在工单系统中接收自然语言请求，由语言模型生成对应的工具名称和参数，再由应用程序执行工单操作。最小业务链路包含三项操作：创建工单、查询工单、关闭工单。

本实验的输入是三条英文工单请求，目标输出是可解析的工具调用 JSON。应用侧还需要完成参数校验、写操作审批控制、SQLite 数据持久化与结果回读。验收以 模型真实生成的工具提议 和 数据库实际状态 为准。

操作 输入中的关键字段 期望工具提议 业务状态检查
创建 request_key=demo-0001，title=Cannot log in create_ticket 未审批不创建；批准后生成 open 工单
查询 ticket_id=1 get_ticket 返回已有工单，状态不变
关闭 ticket_id=1 close_ticket 未审批不关闭；批准后回读到 closed

实验规模限定为三条固定英文请求，用于验证端到端技术链路，不作为工具选择准确率测试。

3. 核心实现与代码讲解

本节按实际执行顺序说明 tool_call_e2e.py 与复用的 ticket_store.py。核心链路由模型推理、结果解析、业务参数校验、执行许可和 SQLite 持久化组成。各步骤的输入、输出和失败条件彼此独立，便于替换模型或业务系统时定位改造范围。

3.1 工具声明：函数接口怎样提供给模型

源文件：tool_call_e2e.py，第 25–61 行（私有仓库）。程序把每个工具拆为 名称、功能描述、参数 Schema。下面是源代码节选：

TOOL_PARAMETERS = {
    "create_ticket": {
        "type": "object", "additionalProperties": False,
        "required": ["request_key", "title"],
        "properties": {
            "request_key": {"type": "string", "pattern": "^[a-z0-9-]{4,32}$"},
            "title": {"type": "string", "minLength": 3, "maxLength": 100}
        },
    },
    # 另有 get_ticket、close_ticket；均要求整数 ticket_id >= 1
}
TOOLS = [
    {"type": "function", "function": {
        "name": name,
        "description": DESCRIPTIONS[name],
        "parameters": schema
    }}
    for name, schema in TOOL_PARAMETERS.items()
]

实现要点： TOOLS 的外层 type="function" 告诉聊天模板这是一个可供模型选择的函数；description 告诉模型函数负责的业务动作；parameters 给出模型应填充的字段结构。模型利用这些信息输出 name 和 arguments。request_key 是同一次创建请求的稳定标识，标题长度限制为 3–100 字符；读取和关闭工具使用 ticket_id。

这里的 Schema 有两个用途：给模型提供接口约定，以及 给应用侧提供强制校验规则。模型即使看到 Schema，仍可能输出不合规字段，所以后续执行器必须再次验证。additionalProperties=False 能禁止未声明的字段进入执行层，例如模型输出的 approved 不能被当成授权凭据。上述代码中的 # 为教程为说明省略项添加的注释，完整工具定义以链接源码为准。

3.2 模型输入与生成：自然语言怎样变为工具提议

源文件：propose()，第 107–133 行。模型消息由系统指令和用户请求组成，工具定义作为 apply_chat_template() 的独立参数传入：

prompt = tokenizer.apply_chat_template(
    msgs, tools=TOOLS, tokenize=False, add_generation_prompt=True
)
inputs = tokenizer(prompt, return_tensors="pt", truncation=True, max_length=1800)
with torch.inference_mode():
    tokens = model.generate(
        **inputs, do_sample=False, max_new_tokens=140,
        pad_token_id=tokenizer.eos_token_id
    )
text = tokenizer.decode(
    tokens[0][inputs["input_ids"].shape[1]:], skip_special_tokens=True
).strip()

实现要点： apply_chat_template() 负责按 Qwen2.5 的聊天格式组织角色消息和工具声明。add_generation_prompt=True 让输入停在模型应开始回答的位置；tokenize=False 表示先得到完整提示文本，再由 tokenizer(...) 转为张量。torch.inference_mode() 关闭梯度跟踪，适合只做推理的链路。

model.generate() 返回的 token 序列包含提示词和新生成内容，因此使用 inputs["input_ids"].shape[1] 切片，只解码模型新生成的 token。若直接解码整个序列，解析器可能读到输入中的工具定义或用户文本。do_sample=False 采用非采样生成，便于固定案例复现，但不能保证不同模型版本、环境下始终选择正确工具；max_new_tokens=140 是本次短工具输出的生成预算，复杂参数可能需要调整。

propose() 返回 user_request、raw_model_output、model_proposal 和 prompt_format，因此实验能够区分用户原始输入、模型真正生成的文本与解析结果。

3.3 输出解析：只接受一个结构完整的工具调用

源文件：parse_tool_call()，第 61–77 行。模型在本实验中输出包含 <tool_call> 标签的文本。执行器要求输出完全满足既定格式：

CALL_REGEX = re.compile(r"<tool_call>\s*(\{.*?\})\s*</tool_call>", re.DOTALL)

def parse_tool_call(generated: str) -> dict:
    matches = list(CALL_REGEX.finditer(generated))
    if len(matches) != 1:
        raise ValueError("Model must emit exactly one complete tool_call block")
    if generated[:matches[0].start()].strip() or generated[matches[0].end():].strip():
        raise ValueError("Model emitted text outside tool_call")
    obj = json.loads(matches[0].group(1))
    if not isinstance(obj, dict) or set(obj) != {"name", "arguments"}:
        raise ValueError("Tool call envelope must contain exactly name and arguments")
    if not isinstance(obj["name"], str) or not isinstance(obj["arguments"], dict):
        raise ValueError("Tool name and arguments must have correct types")
    return obj

实现要点： 正则表达式定位完整标签块，finditer() 控制只能出现一次，块外文字检查阻止模型在调用前后混入说明文本。json.loads() 负责真正的 JSON 解析，随后检查外层只有 name、arguments 两个键，且类型正确。任一步不符合约定都会抛出异常，业务方法不会被调用。

这段解析逻辑专用于本实验使用的 Qwen 文本模板，并非通用 JSON 语法解析器。改用服务商原生 Tool Calling API 时，应优先解析 API 返回的结构化工具字段，而不是照搬该标签正则。解析格式正确只证明输出可读取，工具是否允许及参数是否合格由下一步检查。

3.4 参数校验：执行前重新验证模型输出

源文件：validate_proposal()，第 79–86 行。

def validate_proposal(proposal: dict) -> dict:
    if not isinstance(proposal, dict) or set(proposal) != {"name", "arguments"}:
        raise ValueError("Invalid tool call envelope")
    name = proposal["name"]
    if not isinstance(name, str) or name not in TOOL_PARAMETERS:
        raise ValueError("Unknown or disallowed tool")
    Draft202012Validator(TOOL_PARAMETERS[name]).validate(proposal["arguments"])
    return proposal

实现要点： 先按工具名检查白名单，随后为当前工具选取对应的 JSON Schema。Draft202012Validator.validate() 校验必填字段、字段类型、范围和额外属性；失败时抛出 ValidationError。例如 ticket_id="1" 是字符串而非整数，会在这里被拒绝；drop_database 不在白名单中，也无法执行。

校验与业务执行分离后，既可针对解析器测试格式容错，也可针对验证器独立构造越界输入。这里的校验属于接口结构与数值约束，企业应用还需要独立完成调用人的身份识别、工单归属检查、资源权限和业务状态检查。

3.5 审批与路由：模型不能自行给写操作授权

源文件：execute_proposal()，第 89–104 行。

def execute_proposal(proposal: dict, store: TicketStore, *, allow_mutation: bool) -> dict:
    validate_proposal(proposal)
    name = proposal["name"]
    args = proposal["arguments"]
    if name in ("create_ticket", "close_ticket") and not allow_mutation:
        return {"status": "DENIED_NO_APPROVAL", "name": name, "executed": False}
    if name == "create_ticket":
        record = store.create(args["request_key"], args["title"])
    elif name == "get_ticket":
        record = store.get(args["ticket_id"])
    elif name == "close_ticket":
        record = store.close(args["ticket_id"])
    else:
        raise AssertionError("Unreachable tool")
    return {"status": "EXECUTED", "name": name, "executed": True, "ticket": record}

实现要点： 执行器以“先校验、再授权、最后调用存储”的顺序处理提议。allow_mutation 是业务应用在调用函数时传入的独立关键字参数；模型只提供 proposal，无法通过向 arguments 增加字段来修改它。未批准时直接返回 executed=False，不会进入 store.create() 或 store.close()；读取工具在本 Demo 中不受此布尔写入闸门控制。

这一层是可替换的业务执行入口。接入真实服务时，allow_mutation 应由经过认证的身份、资源权限和审批状态共同决定，不能让用户消息或模型自行设置。读取权限也需要单独校验。get_ticket() 在记录不存在时可能返回 None；本次固定案例用断言确认记录存在，生产接口还需将空记录、存储异常映射为明确的业务错误。

3.6 SQLite 幂等：重复创建为什么不会产生第二张工单

业务实现位于 projects/01-mcp-ticket/ticket_store.py，第 15–48 行。Demo 14 直接调用这一现有模块。建表和创建逻辑的关键源码为：

# 建表约束中的关键字段（代码节选）
request_key TEXT NOT NULL UNIQUE,
status TEXT NOT NULL DEFAULT 'open'
    CHECK(status IN ('open', 'closed'))

# TicketStore.create() 中的关键操作（代码节选）
with self._connect() as db:
    db.execute("INSERT OR IGNORE INTO tickets(request_key,title) VALUES (?,?)",
               (request_key, title))
    row = db.execute("SELECT * FROM tickets WHERE request_key = ?",
                     (request_key,)).fetchone()
    if row["title"] != title:
        raise ValueError("idempotency key reused with different title")
    return dict(row)

实现要点： request_key 的唯一索引在数据库层限制重复插入；INSERT OR IGNORE 遇到已有请求键时保留原行，随后按 request_key 查回记录。同一请求键、同一标题重复调用 create()，返回原工单 ID；如果请求键相同但标题不同，则通过标题比较抛出错误，防止悄悄把不同业务请求当成同一次操作。SQL 中的 ? 是参数占位符，避免拼接文本形成 SQL 注入风险。

本次实测的同一创建请求重试后仍是 id=1、总数为 1。TicketStore.close() 通过 UPDATE ... WHERE id=? 修改状态并再次 SELECT，不存在的工单会抛出 ValueError；关闭后的独立新实例回读验证了状态已持久化。幂等约束发生在业务存储层，不是由大模型保证。 更复杂的生产系统还需要明确请求键有效期、并发重试、事务隔离和审计策略。

3.7 测试与证据：区分模型输出、模拟错误和数据库结果

源文件：run()，第 136–237 行。测试顺序是模型提议创建 → 未授权拒绝 → 授权创建 → 重试同一请求 → 模型提议查询 → 模型提议关闭 → 未授权拒绝 → 授权关闭 → 数据库新实例回读。核心断言节选：

created = propose(model, tokenizer,
    'Create a support ticket. The request_key is "demo-0001" and the title is "Cannot log in".')
assert created["model_proposal"]["name"] == "create_ticket"
denied = execute_proposal(created["model_proposal"], store, allow_mutation=False)
assert denied["status"] == "DENIED_NO_APPROVAL" and store.count() == 0
approved = execute_proposal(created["model_proposal"], store, allow_mutation=True)
ticket_id = approved["ticket"]["id"]
retry = execute_proposal(created["model_proposal"], store, allow_mutation=True)
assert retry["ticket"]["id"] == ticket_id and store.count() == 1

实现要点： propose() 在每条正常请求上真实调用预训练模型，assert 将模型选择工具、参数值和数据库读回纳入运行是否成功的条件。源码还另外用程序构造四个异常提议检查 Schema 与白名单，记录在 crafted_invalid_proposals_rejected；这些反例不能计为“模型主动犯错”。

tool_call_e2e.py 会把成功结果写入 tool_call_evidence.json；推理或断言异常时，main() 写入 REAL_LLM_TOOL_CALL_BLOCKED 失败记录并重新抛出异常，使 CI 显示失败。随后 verify_evidence.py 对 JSON 中三次模型提议、审批拒绝、SQLite 状态、四个构造反例等字段做独立文件核验；它本身不重新加载模型推理。这样的分层能分别检查“真实执行是否通过”和“保留下来的证据是否符合预期”。

5. 工程集成方式

在企业应用中，可把工具调用处理拆成三个接口层：

  1. 模型适配层：传入用户请求、允许的工具定义，输出候选 name/arguments；记录原始模型输出与模型版本。
  2. 业务执行网关：解析并校验候选调用；结合登录用户身份、资源权限、动作风险和审批状态计算执行许可；对写操作保留审计与幂等信息。
  3. 业务服务层：把通过审核的工具调用映射为现有工单 API 或服务方法，返回工单 ID、状态、执行错误及持久化回读结果。

Demo 14 的 execute_proposal() 可以作为执行网关的最小结构示例。工程改造时可保留 propose() → parse_tool_call() → validate_proposal() 的接口边界，将 allow_mutation 替换为基于认证上下文的权限判定，并将 store.create/get/close 替换为业务 API 调用。接入现有 HTTP 工单服务时，需要替换 TicketStore 的直接调用，增加接口认证、错误处理、超时、重试与审计。若使用 MCP，可把业务服务包装为 MCP Server，并由应用的 MCP Client 执行调用；工具调用提议与执行授权的责任划分仍需保留。

适用范围是自然语言表达存在变化、工具接口明确、动作有可校验业务结果的流程。高风险写入操作应由业务权限系统和审批流程作最终决定，不能仅依赖模型的输出。

6. 技术边界与证据入口

本次已验证三条英文请求上的模型工具选择、参数提取、Schema 校验、应用布尔审批、SQLite 写入与回读，以及四个构造非法输入的拒绝。尚未验证跨用户权限、多语言工具选择准确率、并发、提示词注入、生产审计、完整人审工作流和模型跨版本稳定性。
