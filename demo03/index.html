OpenTelemetry：跨服务请求怎样形成可追溯链路？

企业业务调用跨越网关、后端服务和多个进程时，单条日志很难解释一次请求的整体过程。分布式追踪把同一请求上的 Span 关联起来，让人知道每一段调用在哪里发生以及失败从何而来。

01｜这项技术要解决什么问题

企业业务调用跨越网关、后端服务和多个进程时，单条日志很难解释一次请求的整体过程。分布式追踪把同一请求上的 Span 关联起来，让人知道每一段调用在哪里发生以及失败从何而来。

02｜核心技术与实现机制

先用官方 OpenTelemetry Python SDK 在真实独立的网关和后端进程之间传递 W3C traceparent，并以 OTLP/HTTP Protobuf 输出遥测。早期本地探针完成协议级验证；后续 GitHub Actions 的 Docker E2E 启动 Collector 与 Jaeger，从查询接口回读真实 Trace。

03｜实际实验输入与执行过程

Docker 流程构建并启动多个服务，产生六次受控 HTTP 请求，等待 Collector 转发到 Jaeger，并检查回读的六条 Trace 含预期的两项服务及业务 Span。协议探针的原始 .pb、解码 JSONL 和请求日志提供额外证据。

04｜真实验收与观察到的结果

真正的 Collector→Jaeger 六条 Trace 专项 E2E 已在 GitHub-hosted Docker 环境成功。原始 README 中“本地机器没有 Docker”的限制是实验早期条件，并不是最后结项状态。

06｜能力边界与下一步深入方向

演示使用合成业务、回环网络和内存 Trace 存储；没有跨机部署、持续存储、生产鉴权、采样策略、真实业务负载或吞吐 SLO。Jaeger 内部查询接口不是稳定公开 API 保证。
