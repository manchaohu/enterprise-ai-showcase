Demo 14 | LLM Tool Calling: Ticket Creation, Lookup, and Closure

Engineering tutorial — English parity draft, 23 October 2026. The Chinese Demo 14 v0.4 is author-approved. This English text independently requires editorial review. Source: projects/14-real-tool-calling/ (private). Actual CPU experiment #39354577538; original evidence: tool_call_evidence.json (privately archived).

1. Technical requirement and acceptance criteria

The application receives support-ticket instructions expressed in natural language. A pretrained language model must propose a function name and structured arguments for one of three supported operations: create a ticket, look up a ticket, or close a ticket. The surrounding Python application is responsible for parsing the proposal, checking that the function and arguments are allowed, enforcing a write-approval boundary, executing the database operation, and reading the persisted result back from SQLite.

The test has three short, fixed English requests. Success requires that the actual Qwen model emits create_ticket, get_ticket, and close_ticket with the expected parameters, that unapproved mutations do not change SQLite, and that approved mutations do. A replayed create_ticket request must preserve the same ticket ID and row count. This is an executable end-to-end sample, not an accuracy benchmark for arbitrary instructions.

Operation Request / expected proposal Database acceptance check
Create request_key="demo-0001", title="Cannot log in" → create_ticket Denied before approval; approved request inserts one open ticket
Read ticket_id=1 → get_ticket Returns the existing open ticket without mutation
Close ticket_id=1 → close_ticket Denied before approval; approved request changes the status to closed

2. Architecture and component responsibilities

User instruction
   ↓
Qwen2.5-0.5B-Instruct + HF Transformers tools-aware chat template
   ↓  actual <tool_call> JSON text generated by the model
Strict output parser (exactly one block; no outside prose)
   ↓
Allowed function name + Draft 2020-12 JSON Schema validation
   ↓
Application-supplied allow_mutation flag
   ├─ denied create/close → DENIED_NO_APPROVAL, no database changes
   └─ permitted call → TicketStore → SQLite → persistent state readback

Qwen/Qwen2.5-0.5B-Instruct performs tool selection and argument extraction on CPU. transformers and torch execute the model; jsonschema validates the structured proposal. The existing projects/01-mcp-ticket/ticket_store.py supplies the business operations. This experiment imports TicketStore directly; it does not use MCP transport or a hosted model provider's native function-calling API. Demo 01 examines the separate MCP client–server communication path.

3. Core implementation and code explanation

3.1 Declaring callable tools and parameter contracts

Source: tool_call_e2e.py, lines 25–61. The application builds a list of function descriptions from TOOL_PARAMETERS and a separate human-readable description mapping. The excerpt below shows the create operation; the original source also defines get_ticket and close_ticket with a positive integer ticket_id.

TOOL_PARAMETERS = {
    "create_ticket": {
        "type": "object", "additionalProperties": False,
        "required": ["request_key", "title"],
        "properties": {
            "request_key": {"type": "string", "pattern": "^[a-z0-9-]{4,32}$"},
            "title": {"type": "string", "minLength": 3, "maxLength": 100}
        }
    },
    # get_ticket and close_ticket omitted from this excerpt.
}
TOOLS = [
    {"type": "function", "function": {
        "name": name, "description": DESCRIPTIONS[name], "parameters": schema
    }}
    for name, schema in TOOL_PARAMETERS.items()
]

The outer type="function" identifies a callable tool for the chat template; description conveys the intended business action and parameters communicates the expected argument object. The schema serves two distinct purposes: the model receives an interface contract, and the application later enforces the same contract. A model can still generate invalid arguments. additionalProperties=False rejects undeclared keys, including a fabricated approved field. The request_key is a stable idempotency identifier; it is not an authentication or approval token.

3.2 Formatting messages and generating model output

Source: propose(), lines 107–133. A system message instructs the model to emit one tool call and no invented tool result; the user's natural-language request is appended as a separate message.

prompt = tokenizer.apply_chat_template(
    msgs, tools=TOOLS, tokenize=False, add_generation_prompt=True
)
inputs = tokenizer(prompt, return_tensors="pt", truncation=True, max_length=1800)
with torch.inference_mode():
    tokens = model.generate(
        **inputs, do_sample=False, max_new_tokens=140,
        pad_token_id=tokenizer.eos_token_id
    )
text = tokenizer.decode(
    tokens[0][inputs["input_ids"].shape[1]:], skip_special_tokens=True
).strip()

apply_chat_template() serializes roles and tool descriptions using Qwen's chat format. add_generation_prompt=True prepares the continuation point; tokenize=False returns the prompt string before tokenization. torch.inference_mode() disables autograd bookkeeping. do_sample=False makes this fixed small test more repeatable but does not establish deterministic routing under every model revision or runtime. max_new_tokens=140 caps the generated answer length.

The slice [inputs["input_ids"].shape[1]:] removes tokens belonging to the prompt. Parsing the whole returned sequence could inadvertently include echoed tool definitions or user messages. propose() records the user instruction, the raw generated text, and the parsed proposal separately; downstream verification can therefore distinguish model output from application-side interpretation.

3.3 Rejecting malformed or ambiguous output

Source: parse_tool_call(), lines 61–77. The parser locates complete <tool_call> ... </tool_call> blocks and requires exactly one. It rejects any non-whitespace outside that block, parses the payload as JSON, checks that the outer object contains exactly name and arguments, and verifies their types.

matches = list(CALL_REGEX.finditer(generated))
if len(matches) != 1:
    raise ValueError("Model must emit exactly one complete tool_call block")
if generated[:matches[0].start()].strip() or generated[matches[0].end():].strip():
    raise ValueError("Model emitted text outside tool_call")
obj = json.loads(matches[0].group(1))
if not isinstance(obj, dict) or set(obj) != {"name", "arguments"}:
    raise ValueError("Tool call envelope must contain exactly name and arguments")

This deliberately strict format fails closed rather than extracting a promising-looking JSON substring from a verbose answer. It does not mean the regular expression is a general-purpose streaming protocol parser; a production client may need native structured outputs, framed messages, or incremental parsing. If Qwen emits explanatory text or incomplete tags, this Demo rejects the response instead of executing a guessed function.

3.4 Allowlist and JSON Schema validation

Source: validate_proposal(), lines 79–86.

name = proposal["name"]
if not isinstance(name, str) or name not in TOOL_PARAMETERS:
    raise ValueError("Unknown or disallowed tool")
Draft202012Validator(TOOL_PARAMETERS[name]).validate(proposal["arguments"])
return proposal

The allowlist blocks arbitrary function names even when the proposed JSON is syntactically valid. The Draft 2020-12 validator then checks required keys, field types, regex patterns, numeric bounds, and extra properties for that specific function. Validation happens after model inference and before any business side effect. A valid schema is necessary but insufficient for authorization; an argument object containing a valid ticket_id must still pass the separate mutation gate.

3.5 Mutation approval and business execution

Source: execute_proposal(), lines 89–105.

def execute_proposal(proposal, store: TicketStore, *, allow_mutation: bool):
    validate_proposal(proposal)
    name = proposal["name"]
    args = proposal["arguments"]
    if name in ("create_ticket", "close_ticket") and not allow_mutation:
        return {"status": "DENIED_NO_APPROVAL", "name": name, "executed": False}
    if name == "create_ticket":
        record = store.create(args["request_key"], args["title"])
    elif name == "get_ticket":
        record = store.get(args["ticket_id"])
    elif name == "close_ticket":
        record = store.close(args["ticket_id"])
    return {"status": "EXECUTED", "name": name, "executed": True, "ticket": record}

Excerpt: the source contains an additional unreachable-case assertion. The boolean allow_mutation is supplied by trusted application code, never parsed from model-generated arguments. The guard covers create_ticket and close_ticket; get_ticket is treated as read-only in this sample. Denial returns before a write reaches SQLite. This boolean is a demonstration boundary, not an authenticated human approval process, identity check, or role-based access control framework. In a real deployment, pass an authorized decision derived from your application identity, permissions, policy, and audit layer.

3.6 SQLite idempotency and state transitions

Source: ticket_store.py, lines 16–48.

# Part of the tickets table schema:
request_key TEXT NOT NULL UNIQUE,
status TEXT NOT NULL DEFAULT 'open' CHECK(status IN ('open', 'closed'))

# Inside TicketStore.create():
db.execute("INSERT OR IGNORE INTO tickets(request_key,title) VALUES (?,?)",
           (request_key, title))
row = db.execute("SELECT * FROM tickets WHERE request_key = ?", (request_key,)).fetchone()
if row["title"] != title:
    raise ValueError("idempotency key reused with different title")
return dict(row)

The SQLite UNIQUE constraint prevents two ticket rows sharing one request_key. INSERT OR IGNORE plus a follow-up lookup returns the existing row for a repeated, identical request. The title equality check rejects the same key being reused for a conflicting command. Parameterized ? queries avoid constructing SQL by concatenating user content. The table's status CHECK constraint restricts the stored lifecycle to open and closed.

Repeated creation was tested against the actual store: the ID remained 1 and the row count remained 1. The experiment also closes the record, creates a fresh TicketStore instance, and reads closed back from the same SQLite file. The design is intentionally compact; distributed idempotency keys, auth, concurrent request semantics, and audit retention need additional engineering.

3.7 Evidence generation, independent checking, and troubleshooting

Source: run(), lines 136–237 and verify_evidence.py. The test calls the pretrained model for each positive request. For create/close it attempts the same model-generated proposal first without permission, then with allow_mutation=True; it verifies the expected database change. Four additional program-constructed invalid proposals exercise malformed arguments, a fabricated approval field, a disallowed tool, and a string substituted for an integer ID. They are not claimed to be errors produced by the model.

The E2E script writes REAL_LLM_TOOL_CALL_E2E_PASS and the raw model messages into tool_call_evidence.json. On failure it writes REAL_LLM_TOOL_CALL_BLOCKED and raises an exception. verify_evidence.py reads the saved JSON and checks the three proposals, denial results, database readback, and four negative tests. The verifier does not run model inference again.

Symptom Start debugging here Check
No valid single <tool_call> propose(), parse_tool_call() Raw output, chat template, max token budget, extra prose
Correct function but rejected arguments validate_proposal() Required keys, schema type, regex, extra fields
Write never happens execute_proposal() Trusted allow_mutation, DENIED_NO_APPROVAL
Duplicate ticket created or key conflict TicketStore.create() Unique key, stored title, transaction and count
Evidence checker fails run(), verify_evidence.py Current run JSON, events, sqlite_readback, negative cases

5. Integration into an enterprise service

Keep the model proposal adapter separate from application policy and business execution. In an HTTP or worker service, replace the three hardcoded user requests with a request DTO, and map the DTO to the model's role/messages format. Log raw tool proposals and parser rejections with sensible privacy controls. Replace the demo boolean with an application-originating authorization decision tied to a principal, a concrete tool call, the exact arguments, and an expiry/replay policy. Call existing business APIs or an actual MCP client behind the policy gate, rather than granting the model direct database access.

Store operation IDs/idempotency keys at the business boundary. Return structured success and denial states; provide retry behavior only after deciding which operations are replay-safe. The Demo proves one local SQLite path, not networked approval, multi-user authorization, distributed transactions, or production reliability.

6. Verified scope and limitations

  • Only three short English positive requests; no measured tool-routing accuracy on varied languages or difficult inputs.
  • Application approval is a trusted boolean supplied by the caller, not a verified human workflow.
  • Function proposals are generated using Hugging Face tools-aware chat formatting, not a hosted provider-native tool-call API; execution directly imports TicketStore, not MCP transport.
  • Four negative samples were constructed by the test, not generated by Qwen.
  • Model main was requested; the observed resolved SHA is preserved for traceability, but the experiment did not pin MODEL_REVISION to that immutable SHA.
  • Private source is inaccessible to anonymous site readers; reproduction requires repository authorization. CI success is a narrow Demo outcome rather than production certification.
