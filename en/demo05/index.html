Durable SQLite queues: idempotency, retries and leases

Long-running background work needs durable states, retry rules and idempotent submissions. Otherwise duplicate requests, transient failure and worker crashes can create lost tasks or inconsistent business changes.

← All 27 demos

01 · The problem this technology solves

Long-running background work needs durable states, retry rules and idempotent submissions. Otherwise duplicate requests, transient failure and worker crashes can create lost tasks or inconsistent business changes.

02 · Core mechanism

A transactional Python/SQLite queue implements idempotent keys, leased claiming, delayed retries, expired-lease recovery, bounded attempts, dead-letter states and completion. The verifier advances a simulated logical clock instead of launching a real long-running worker fleet.

03 · What the experiment actually ran

Reusing an identical request key must return the same job ID; reusing it for a different command must fail. The test then advances retry delays, simulates an abandoned worker lease, reclaims it, reaches dead-letter state and finishes a separate job.

04 · Observed acceptance evidence

SQLite transitions and checks succeeded, recording ASYNC_SQLITE_QUEUE_E2E_PASS, dead/done states, attempts, duplicate handling and explicit simulated_logical_clock evidence.

05 · Reproduce the experiment

From the repository root, use the experiment's documented runner. This snippet is a reference command, not a live in-browser executable.

cd projects/05-async-queue

Model downloads, external tools, OS-specific requirements and permissions are described in the private project.

06 · Limits and the next deeper question

No true process-level worker deployment, concurrent load, Redis/RabbitMQ integration or cross-machine recovery testing. Lease behavior under a simulated clock is not a proof of distributed queue reliability.
