Agent tool approval: gate side effects before execution

Agent-driven write operations should be gated before database effects. Authorization must be tied to the exact tool, arguments and target rather than treated as a reusable vague approval.

01 · The problem this technology solves

Agent-driven write operations should be gated before database effects. Authorization must be tied to the exact tool, arguments and target rather than treated as a reusable vague approval.

02 · Core mechanism

An in-process ApprovalGate protects real SQLite TicketStore operations. It rejects missing approvals, requester self-approval, unapproved calls, mutated arguments, reused approvals and non-allowlisted tool names, then records audit events.

03 · What the experiment actually ran

One test ticket starts open. Multiple unauthorized closures must leave it unchanged. A simulated reviewer role approves the exact close_ticket arguments, allowing one genuine SQLite update; replaying that approval must be denied.

04 · Observed acceptance evidence

The real SQLite close effect, preapproval denial, one-time approval consumption and audit events were verified. The evidence stores APPROVED, EXECUTED and DENIED events.

06 · Limits and the next deeper question

The reviewer is a simulated role, not an authenticated human. No real identity proof, signed approval, MCP transport, concurrency hardening or deployable policy security has been evaluated.
