1. Requirements and acceptance

Wrap a side-effecting close-ticket tool with an approval record. The agent may request closure, the reviewer role string authorizes a particular payload, and execution consumes approval once. Negative tests cover disallowed tools, parameter mismatch, repeated use and unauthorized actors.

2. Technical design and data flow

ApprovalGate stores approvals and audit records in a separate SQLite file and delegates ticket effects to the Demo 01 store. An approval binds requester, tool and canonicalized arguments. A conditional UPDATE consumes an approved record exactly once. Role names in this test are caller-supplied strings, not authenticated human identities.

3. Core code and implementation details

3.1 Restrict request tool and payload

if actor != "agent" or tool != "close_ticket" or set(args)!={"ticket_id"}:
    self.record(actor,"DENIED",None,"not permitted for approval")
    raise PermissionError("not permitted")
arguments = json.dumps(args, sort_keys=True)

Only close_ticket with ticket_id is allowed. JSON key sorting gives stable serialized arguments for later matching. Production code would also validate value types and derive roles from authenticated user/session context.

3.2 Single-use approval and audit boundary

Source：approval_gate.py — Selected excerpt, surrounding context omitted; not standalone executable

db.execute("BEGIN IMMEDIATE")
cursor = db.execute("""UPDATE approvals SET state='consumed'
 WHERE id=? AND requester=? AND tool=? AND args_json=? AND state='approved'""",
 (approval_id,actor,tool,arguments))
if cursor.rowcount!=1:
    db.rollback()
    raise PermissionError("no matching active approval")

The conditional state transition prevents a second execution. However, approval consumption is committed in one SQLite DB before the ticket effect in another DB; the two changes are not atomic. A failed close can leave the approval consumed, requiring compensation or transactional redesign.

5. Integration and operational use

Integrate real identity, reviewer sessions, expiry, human UI and policy checks. For sensitive changes, require maker-checker separation and audit provenance. Recheck access at execution time; approval of a request is not a permanent authorization grant.
