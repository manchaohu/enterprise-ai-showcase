01 · The problem this technology solves

A ticket assistant is useful only if it can execute operations, not merely describe them. This experiment demonstrates official MCP client/server discovery, typed tool calls and persisted SQLite ticket updates rather than a fabricated tool transcript.

02 · Core mechanism

The official Python MCP SDK connects a stdio client to a separate server process. After session initialization, the client lists three tools and invokes them with structured arguments. TicketStore persists state in SQLite; repeated calls with the same request key are checked for idempotency.

03 · What the experiment actually ran

The test starts a real stdio MCP server with an isolated temporary SQLite database. It creates a 'Cannot log in' ticket, repeats the same request key, reads and closes the record, retries the close, and independently checks that only one ticket remains. No LLM chooses these calls in this demo.

04 · Observed acceptance evidence

The accepted GitHub Actions E2E demonstrates real MCP SDK discovery, invocation and durable ticket state with status OFFICIAL_MCP_STDIO_PASS. Older import notes describing unverified SDK transport refer to the initial archive stage, not this later independently implemented example.

05 · Reproduce the experiment

From the repository root, use the experiment's documented runner. This snippet is a reference command, not a live in-browser executable.

cd projects/01-mcp-ticket
python -m pip install -r requirements.txt
python verify_mcp.py

Model downloads, external tools, OS-specific requirements and permissions are described in the private project.

06 · Limits and the next deeper question

There is no authenticated authorization, multi-tenant isolation, network MCP deployment, concurrent recovery testing or approval workflow. Unlike Demo 14, a pretrained model does not autonomously propose the tool calls.
