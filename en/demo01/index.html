1. Requirements and acceptance

Expose create, read and close operations through an MCP server. An MCP client must discover the tools, call them over stdio and verify persistent changes in SQLite. Two creates using request_key=case-001 must produce one ticket; read and close must work.

2. Architecture and execution path

The client launches a FastMCP server over stdio. Server handlers dispatch calls to TicketStore, which writes to SQLite. The test establishes ClientSession, lists tools and invokes them. No LLM selects tools here; that is the separate Demo 14 concern.

3. Core implementation

3.1 Declare MCP tools

Source：server.py · Selected excerpt; full logic in repository

mcp = FastMCP("enterprise-ticket")
@mcp.tool()
def create_ticket(request_key: str, title: str) -> dict:
    return store.create(request_key, title)
if __name__ == "__main__":
    mcp.run(transport="stdio")

@mcp.tool() exposes a typed Python function as an MCP tool. TicketStore is the persistence boundary. stdio carries protocol messages, so arbitrary stdout logging can corrupt the transport. This server has no network authentication or HTTP gateway.

3.2 Client initialization and result handling

Source：verify_mcp.py · Selected excerpt; full logic in repository

params = StdioServerParameters(
    command=sys.executable, args=[str(ROOT / "server.py")], env=env)
async with stdio_client(params) as (reader, writer):
    async with ClientSession(reader, writer) as session:
        await session.initialize()
        tools = await session.list_tools()
        first = payload(await session.call_tool("create_ticket", {
            "request_key":"case-001", "title":"Cannot log in"}))

StdioServerParameters starts a child process with a temporary database path. The payload() helper checks MCP error flags, prefers structuredContent and falls back to JSON text blocks. Calling via ClientSession makes the transport itself part of the test.

3.3 SQLite uniqueness and idempotent retries

Source：ticket_store.py · Selected excerpt; full logic in repository

db.execute("INSERT OR IGNORE INTO tickets(request_key,title) VALUES (?,?)",
           (request_key, title))
row = db.execute("SELECT * FROM tickets WHERE request_key = ?",
                 (request_key,)).fetchone()
if row["title"] != title:
    raise ValueError("idempotency key reused with different title")

request_key has a SQLite UNIQUE constraint. A retry with the same title returns the existing row; a conflicting title raises an error. Bound ? parameters separate SQL from values. This is local business idempotency, not a distributed transaction guarantee.

5. Integration and operational design

Reproduction commands (requires private repo access)

cd projects/01-mcp-ticket
python -m pip install -r requirements.txt
python verify_mcp.py

Replace TicketStore with a business-service adapter while keeping stable idempotency keys and response shapes. Network deployments need authentication, authorization, audit and rate limiting. Model-driven tool selection can be added upstream, with independent application validation.

6. Limits and evidence

Only local stdio, three tools, SQLite state transitions and retries were exercised. Remote transport, authorization, real approvals, concurrency and distributed transactions remain outside scope.
